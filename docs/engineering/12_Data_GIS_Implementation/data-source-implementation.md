# Data Source Implementation

## 1. Purpose

This document provides an implementation framework for data sources by domain, elaborating [data-sources.md](../04_Data_Engineering/data-sources.md) with acquisition-mechanism detail. **No source is fabricated or claimed obtained.** Where a source is not confirmed, this document writes **SOURCE UNRESOLVED**, per this milestone's explicit instruction.

## 3. Reading the Status Column Correctly

Every domain-level dataset above is marked **SOURCE UNRESOLVED** except Transportation, which carries a **Proposed** category (OpenStreetMap) sourced specifically from the Blueprint's own justification — this is still not a confirmed, accessible, approved source for DistrictMind's actual implementation; it is the strongest-evidenced candidate, restated unchanged from [data-sources.md](../04_Data_Engineering/data-sources.md) Section 3. **No dataset in this document has been obtained.**

## 4. How DistrictMind Intends to Address Fragmentation

The Abstract's own named problem — "population, GIS, health, education, and disaster data exist in disconnected spreadsheets, PDFs, and departmental portals with no unified query layer" — is addressed architecturally, not yet operationally, through:

```mermaid
flowchart LR
    Sources[Different Sources] --> Adapters[Source Adapters]
    Adapters --> Canonical[Canonical Representation]
    Canonical --> Val[Validation]
    Val --> IDRes[Identifier Resolution]
    IDRes --> TempAlign[Temporal Alignment]
    TempAlign --> SpatAlign[Spatial Alignment]
    SpatAlign --> Prov[Provenance]
    Prov --> Curated2[Curated Dataset]
    Curated2 --> Intel[Intelligence]
```

| Mechanism | Purpose | Status |
|---|---|---|
| Canonical schemas | Every domain's Curated shape is fixed regardless of source format ([entity-catalog.md](../05_Database_Design/entity-catalog.md)) | Designed, not yet implemented |
| Identifiers | Stable, assigned identifiers, never mutable natural keys ([entity-catalog.md](../05_Database_Design/entity-catalog.md) Section 4) | Designed |
| Provenance | Every record retains source + ingestion timestamp ([data-lineage-and-provenance-implementation.md](data-lineage-and-provenance-implementation.md)) | Designed |
| Timestamps | Observation vs. ingestion vs. effective time distinguished ([temporal-data-implementation.md](temporal-data-implementation.md)) | Designed |
| Validation | The full rule set in [data-validation-implementation.md](data-validation-implementation.md) | Designed |
| Normalization | Unit/categorical/spatial/temporal normalization ([data-transformation-implementation.md](data-transformation-implementation.md)) | Designed |
| Source precedence | When two sources disagree, a documented precedence rule applies (Section 19 of this milestone, [data-gis-integration.md](data-gis-integration.md) Section 6) | Designed, not yet calibrated (no real conflicting sources exist yet to calibrate against) |
| Reconciliation | Entity matching across sources ([data-transformation.md](../04_Data_Engineering/data-transformation.md) Section 6) | Designed |
| Quality scoring | Conceptual framework only, no numeric thresholds ([data-quality-implementation.md](data-quality-implementation.md)) | Designed |

**This resolution mechanism is architecturally designed and internally consistent, but it is not yet operational** — it has never been exercised against real, conflicting source data, since no source has been confirmed and ingested yet. This is explicitly not claimed as a solved problem.

## 5. Architectural Decision

**AD-DATA-001 — Source Fragmentation Is Addressed at Ingestion Time via Canonical Schema + Identifier + Provenance, Not by Assuming Sources Will Naturally Agree**
- **Context:** DistrictMind's core problem statement is data fragmentation across disconnected sources; the architecture must actively reconcile this, not assume it away.
- **Decision:** Every ingested record, regardless of source, is mapped to a canonical schema, assigned a stable identifier (or matched to an existing one), and carries full provenance — before it is trusted as Curated data (Section 4).
- **Alternatives considered:** Storing each source's data in its own native shape and reconciling only at query time (rejected — this would push fragmentation-handling complexity into every consumer, violating Separation of Concerns and risking inconsistent reconciliation logic across the codebase).
- **Reasoning:** Directly addresses the Abstract's named problem; consistent with Data Integrity and the existing AD-DE-001/AD-DE-002 decisions.
- **Trade-offs:** Requires upfront schema-mapping work per source before any of its data is usable — accepted, since deferring this to query time would be strictly worse (repeated, inconsistent reconciliation logic).
- **Consequences:** [data-transformation-implementation.md](data-transformation-implementation.md) and [data-gis-integration.md](data-gis-integration.md) both assume this canonicalization has already occurred by the time data reaches the Curated layer.
- **Status:** Proposed.
