# Configuration Management

## 1. Purpose

This document defines configuration categories and the strict boundaries between configuration, secrets, source code, user data, and model artifacts. **No actual API key, credential, or secret value appears anywhere in this document.**

## 2. Configuration Categories

| Category | Examples (Conceptual, No Real Values) | Governs |
|---|---|---|
| Application configuration | Log level, feature flags, pagination page size | General backend/frontend behavior |
| Database configuration | Connection host/port (not credentials), pool size | Data Access Layer |
| GIS configuration | Canonical CRS identifier, geometry simplification tolerances | GIS Service |
| AI configuration | Provider endpoint (not the API key itself), model name, context-window limits | AI Orchestration Service |
| Authentication configuration | Token expiry duration, OAuth/OIDC issuer URL | Authentication Service |
| External integration configuration | Ingestion source endpoints, rate-limit parameters | Ingestion Service, Integration adapters |
| Feature flags | Whether a not-yet-stable capability (e.g., an early Prediction domain) is enabled | Any service |
| Environment-specific settings | Per-environment values distinguishing Development/Testing/Staging/Production ([environment-management.md](environment-management.md)) | All of the above |

## 3. The Strict Boundary

| Category | Definition | Where It Lives |
|---|---|---|
| **Configuration** | Non-secret, environment-varying values (Section 2) | Environment variables / configuration files, version-controllable in template form only |
| **Secrets** | Credentials, API keys, tokens, connection passwords | A secrets-management mechanism (Section 6) — **never** in version control, **never** in this or any documentation |
| **Source code** | Application logic | The repository, per [repository-implementation-map.md](repository-implementation-map.md) |
| **User data** | Data entered/generated by DistrictMind users (queries, reviewed Recommendations) | The database, subject to [data-governance.md](../04_Data_Engineering/data-governance.md) |
| **Model artifacts** | Trained model files/weights | A model store, referenced by Model Execution Metadata ([model-lifecycle.md](../07_AI_GIS_and_Intelligence/model-lifecycle.md) Section 4) — never embedded in source code or configuration |

**AD-IMP-002 — Strict Five-Way Separation of Configuration, Secrets, Source Code, User Data, and Model Artifacts**
- **Context:** Without an explicit rule, it is common in fast-moving projects for a secret to end up in a configuration file that gets committed, or for a model artifact to be checked in alongside source code, or for user data to leak into a log treated as configuration — each a real, recurring class of incident in software projects generally.
- **Decision:** These five categories (Section 3) are never colocated or conflated in DistrictMind's implementation — each has its own storage location and handling rule, enforced as a standing implementation discipline, not a one-time check.
- **Alternatives considered:** A single "settings" bucket covering configuration and secrets together for simplicity (rejected — directly risks secret leakage into version control, violating Security by Design); embedding small model artifacts in source code for convenience (rejected — breaks the Model Execution Metadata versioning chain required for Reproducibility, [model-lifecycle.md](../07_AI_GIS_and_Intelligence/model-lifecycle.md)).
- **Reasoning:** Directly required by this milestone's explicit instruction; consistent with Security by Design, Data Integrity, and Reproducibility principles ([engineering-principles.md](../00_Engineering_Overview/engineering-principles.md)).
- **Trade-offs:** Requires more upfront infrastructure decisions (a secrets mechanism, a model store) than a single undifferentiated approach — accepted, since the alternative risk (a leaked secret, an unversioned model) is far costlier than the setup effort.
- **Consequences:** [dependency-management.md](dependency-management.md) and [environment-management.md](environment-management.md) both assume this separation holds in every environment, not only production.
- **Status:** Proposed.

These five categories are never mixed — a configuration file never embeds a secret value, a model artifact is never checked into the same location as source code without explicit version tracking, and user data never appears in a configuration or log file (Section 10, [coding-standards.md](coding-standards.md)).

## 4. Environment Variables — Conceptually

Per [naming-conventions.md](../03_Project_Structure/naming-conventions.md) Section 11: `UPPER_SNAKE_CASE`, prefixed by concern area (e.g., a database-related variable prefixed `DB_`, an AI-provider-related variable prefixed `AI_`) — restated unchanged, not redefined here. No actual variable *value* is ever documented; only the *existence and purpose* of a variable name is described.

## 5. Configuration Validation

Every service validates its required configuration at startup (Section 7) — a missing or malformed configuration value is a startup failure, not a runtime surprise discovered mid-request. This is the Fail-Safe Behavior principle applied specifically to configuration.

## 6. Secret Management

No specific secrets-management tool is confirmed by any prior document ([security-architecture.md](../02_System_Architecture/security-architecture.md) Section 8 marks this an open decision) — this document does not resolve it, and restates it as **Under Evaluation**. Whatever mechanism is eventually chosen, it must satisfy: secrets are never committed to version control, never logged (Section 10), and are injected into the running application at deploy/start time, not baked into any artifact.

## 7. Defaults

Configuration values with a safe, non-sensitive default (e.g., a default pagination page size) may ship with a sensible default; anything security- or correctness-sensitive (a database connection string, an AI provider endpoint) has **no default** — its absence is a startup validation failure (Section 5), never a silent fallback to an unintended value.

## 8. Missing Configuration Behavior

| Scenario | Behavior |
|---|---|
| A required, non-defaultable configuration value is missing | The service fails to start, with a clear (non-sensitive) error identifying which configuration is missing |
| An optional configuration value is missing | The documented default (Section 7) applies |
| A secret is missing | The service fails to start — it never falls back to an unauthenticated or degraded-security mode as a "convenience" |

## 9. Startup Validation

Restated from Section 5: every service performs a configuration-validation pass before accepting any request — this is the implementation-level realization of the Fail-Safe Behavior and Security by Design principles, applied at the earliest possible point in a service's lifecycle.

## 10. Never in Documentation

Per the milestone's explicit instruction: this document — and every document in this entire engineering documentation set — contains no real API key, password, connection string, or token. Any example above uses placeholder/conceptual language only (e.g., "a database connection host/port," not an actual value).
